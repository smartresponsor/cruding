= Cruding

Universal CRUD route processor, route-grammar owner, capability resolver, and resource-payload producer for Symfony host applications.

== Component identity

Cruding is a reusable Symfony bundle with the canonical PSR-4 root `App\Cruding\` mapped directly to `src/`. The component token remains visible in `Crud*` class names, while redundant intermediate `Crud/` directories are intentionally forbidden.

The tree is role-first. Technical responsibilities such as `Controller`, `Resolver`, `Builder`, `Factory`, `Handler`, `Provider`, `Guard`, `Invoker`, `Dispatcher`, `Runner`, `Parser`, `Service`, and `ServiceInterface` appear before feature semantics. Inside `Service`, current semantic branches are `Api`, `Operation`, `Resource`, and `Runtime`.

== Responsibility and boundaries

Cruding owns:

* generic CRUD route delivery and tokenized route grammar;
* CRUD controller and API controller behavior;
* entity, form, capability, ownership, and service resolution;
* generic CRUD operation dispatch;
* resource-bound view route parsing and neutral `CrudResourceContract` payload production;
* API problem responses and mutation guards;
* runtime route policy, lock/inventory inspection, and diagnostics.

Cruding does not own platform menus, external callbacks or webhooks, host shell CSS, or the final cross-component HTML rendering boundary.

== Bundle loading

`CrudingExtension` loads `config/services.yaml`; `CrudingBundle` installs the compiler-pass and bundle integration. Host applications configure Cruding through the `cruding` extension and mount the shipped route resources where generic CRUD processing belongs.

The repository package is `cruding/crud`. Local host applications may install it through a Composer path repository during development.

== Routing contract

Symfony routes are structural delivery routes. Semantic CRUD grammar is resolved in PHP rather than encoded as an expanding route-regex vocabulary. The tokenized resolver determines resource path, operation, view, and identity semantics after route delivery.

Typical generic paths include:

[source,text]
----
/product/index
/product/sample-entry
/product/edit/123
/product/document/verify/sample-entry
----

The host can verify the delivery boundary with `debug:router` and `router:match`; semantic interpretation is then observable through Cruding runtime diagnostics. See `docs/cruding/cruding-tokenized-route-resolver.md` and `docs/cruding/cruding-host-route-integration-verification.md`.

== Resource-view contract

Cruding also handles read-oriented routes whose semantics are still resource-bound:

[source,text]
----
/{resource}/{subject}/{view}
/{resource}/{subject}/{view}/{action}
/{resource}/{subject}/{view}/{item}/{action}
----

The resource controller resolves a `CrudRouteContextDTO`, locates a producer/provider, and returns `CrudResourceContract`. Producer providers must not cross the render boundary by returning Twig rendering or Symfony HTML responses.

For resource-view routes, Cruding owns route tokens and payload production only. Viewing owns the final runtime render decision and may consume Interfacing templates when the host provides that integration. `templateCandidates` are diagnostic/template-location hints, not permission to reintroduce operation-specific rendering ownership into Cruding.

See `docs/cruding/cruding-resource-view-routes.md`.

== Bulk mutation contract

The generic `bulk` operation has its own mutation boundary and never aliases `create`. Hosts provide named `CrudBulkMutationHandlerInterface` services; Cruding resolves exactly one handler, enforces its backend permission, resolves the requested `selected`, `filtered`, or `currentPage` data scope through Tabling and Collectioning, and checks per-object mutation access before invoking the handler.

Each object mutation runs through the existing mutation lifecycle. Handlers explicitly choose whether processing may continue after an object-level failure. Partial-failure responses expose only stable Cruding error codes and batch positions; arbitrary exception messages and internal PHP class names are not part of the client contract.

== Contracts and extension points

* Service contracts live in `ServiceInterface/`; implementation/contract feature branches mirror each other where a true implementation contract exists.
* Object capability contracts live in `Contract/Capability/`.
* DTO classes live in `DTO/` and use the explicit `DTO` suffix.
* Host applications provide concrete entities, repositories, forms, services, provider implementations, capability signals, and configuration maps rather than copying generic CRUD controllers.

== Dependency policy

Cruding must remain usable without hard coupling to optional neighboring UI components. Cross-component integration is expressed through explicit package/public contracts and host-provided namespaces or services, not by assuming neighboring source directories exist.

`composer.lock` and `vendor/` are local development artifacts and are ignored by the repository. Runtime dependencies are declared by `composer.json`.

== Quality contract

The primary repository gate is:

[source,powershell]
----
composer install
composer validate --strict
composer dump-autoload
composer check:cruding
----

`composer check:cruding` runs canonical guards, smoke checks, DTO/tree/PHPDoc enforcement, and PHPUnit. PHPDoc coverage is required for every named source class/interface/trait/enum and every public behavior method other than constructors; specialized array-shape and generic type annotations remain part of the code contract.

Additional static-analysis and refactoring configuration is stored in `phpstan.neon`, `psalm.xml`, `rector.neon`, and `.php-cs-fixer.php`.
